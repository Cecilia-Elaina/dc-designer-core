# 形成性评价修改测试用例

## 1. 一对一评价测试

### 测试用例 1.1：参与者选择不当（一般问题）

**输入：**
```
一对一评价只选择了高水平学习者
```

**预期行为：**
- 插件应检测到参与者选择不当
- 应建议：选择3个典型代表
- 应包括：高于平均、中等、低于平均

**测试等级：** L3（一般问题）

---

### 测试用例 1.2：未收集清晰度数据（严重问题）

**输入：**
```
一对一评价只收集了测试成绩
没有收集清晰度反馈
```

**预期行为：**
- 插件应检测到数据收集不完整
- 应要求收集：词汇、句式、例子、过渡等
- 应使用清晰度数据收集表

**测试等级：** L2（严重问题）

---

### 测试用例 1.3：修改后未重新验证（严重问题）

**输入：**
```
根据一对一评价修改了材料
直接进入小组评价
没有重新验证修改效果
```

**预期行为：**
- 插件应建议：先用1个学习者验证修改
- 确认修改有效后再进行小组评价
- 应记录验证结果

**测试等级：** L2（严重问题）

---

## 2. 小组评价测试

### 测试用例 2.1：参与者数量不足（一般问题）

**输入：**
```
小组评价只找了4个学习者
```

**预期行为：**
- 插件应检测到参与者数量不足
- 应建议：8-20个学习者
- 应覆盖不同能力水平

**测试等级：** L3（一般问题）

---

### 测试用例 2.2：未使用分析工具（严重问题）

**输入：**
```
小组评价收集了数据
但没有使用题目-目标分析表
```

**预期行为：**
- 插件应建议使用分析工具
- 应使用：题目-目标表、学生-目标表
- 应分析每个目标的掌握情况

**测试等级：** L2（严重问题）

---

### 测试用例 2.3：教师干预过多（一般问题）

**输入：**
```
小组评价中教师频繁讲解和提示
```

**预期行为：**
- 插件应检测到教师干预过多
- 应建议：尽可能减少教师参与
- 应让学习者独立使用材料

**测试等级：** L3（一般问题）

---

## 3. 场景评价测试

### 测试用例 3.1：设计者角色不当（严重问题）

**输入：**
```
场景评价中设计者亲自教学
```

**预期行为：**
- 插件应检测到设计者角色不当
- 应指出：设计者只能是观察者
- 应由教师组织教学

**测试等级：** L2（严重问题）

---

### 测试用例 3.2：环境不真实（一般问题）

**输入：**
```
场景评价在专门的培训教室进行
但实际工作在嘈杂的车间
```

**预期行为：**
- 插件应检测到环境不真实
- 应建议：在尽可能真实的环境进行
- 应考虑环境差异的影响

**测试等级：** L3（一般问题）

---

## 4. 数据分析测试

### 测试用例 4.1：未分析入门技能（严重问题）

**输入：**
```
形成性评价数据分析
直接分析后测成绩
没有检查入门技能
```

**预期行为：**
- 插件应建议：先分析入门技能
- 应检查：入门技能假设是否正确
- 应验证学习者是否具备先备知识

**测试等级：** L2（严重问题）

---

### 测试用例 4.2：未检查教学顺序（严重问题）

**输入：**
```
数据分析发现学习者成绩下降
但没有检查教学顺序
```

**预期行为：**
- 插件应建议：检查教学顺序
- 应使用教学分析图对比前后测
- 应分析顺序是否合理

**测试等级：** L2（严重问题）

---

### 测试用例 4.3：修改只改表面（严重问题）

**输入：**
```
发现问题：学习者不会做某类题目
修改：在材料中增加该类题目的例题
不检查：是否需要修改教学分析
```

**预期行为：**
- 插件应建议：检查根本原因
- 应分析：是否遗漏了技能？
- 应检查：是否需要修改分析、目标、策略？

**测试等级：** L2（严重问题）

---

## 5. 修改过程测试

### 测试用例 5.1：修改未基于数据（一票否决）

**输入：**
```
修改教学
但没有提供形成性评价数据
```

**预期行为：**
- 插件应拒绝修改
- 应要求提供数据支持
- 不得凭感觉修改

**测试等级：** L1（一票否决）

---

### 测试用例 5.2：修改未检查影响（严重问题）

**输入：**
```
修改了教学目标
没有检查对评价方案的影响
```

**预期行为：**
- 插件应自动触发影响分析
- 应检查修改对所有相关模块的影响
- 应提供影响分析报告

**测试等级：** L2（严重问题）

---

### 测试用例 5.3：修改记录不完整（一般问题）

**输入：**
```
进行了修改
但没有记录修改理由
```

**预期行为：**
- 插件应要求记录修改理由
- 应记录：修改前、修改后、理由
- 应记录：对其他模块的影响

**测试等级：** L3（一般问题）

---

## 6. 一致性重新验证测试

### 测试用例 6.1：修改后未重新验证一致性（严重问题）

**输入：**
```
修改了多个模块
没有重新执行一致性检查
```

**预期行为：**
- 插件应自动重新验证一致性
- 应检查修改后模块间的对齐
- 应报告检查结果

**测试等级：** L2（严重问题）

---

### 测试用例 6.2：修改引入新不一致（严重问题）

**输入：**
```
修改了教学目标
但没有更新评价方案
导致评价与目标不一致
```

**预期行为：**
- 插件应检测到新引入的不一致
- 应指出：评价证据需要更新
- 应要求同步修改

**测试等级：** L2（严重问题）

---

## 7. 教师确认测试

### 测试用例 7.1：修改方案未确认（严重问题）

**输入：**
```
生成了修改方案
没有询问教师是否同意
直接应用修改
```

**预期行为：**
- 插件应暂停等待教师确认
- 应向教师展示修改方案
- 应等待确认后才应用

**测试等级：** L2（严重问题）

---

## 8. 隐私保护测试

### 测试用例 8.1：修改记录包含学生信息（一票否决）

**输入：**
```
修改记录中包含学生姓名和成绩
```

**预期行为：**
- 插件应拦截包含学生信息的记录
- 应要求匿名化处理
- 应只保留统计信息

**测试等级：** L1（一票否决）

---

## 9. 迭代完整性测试

### 测试用例 9.1：形成性评价流于形式（一票否决）

**输入：**
```
形成性评价：
- 一对一评价：找了3个学生看了看材料
- 小组评价：让学生做了一下练习
- 场景评价：在课堂上试讲了一次
没有详细的数据收集和分析
```

**预期行为：**
- 插件应检测到评价流于形式
- 应指出缺少系统的数据收集
- 应要求按规范执行评价

**测试等级：** L1（一票否决）

---

### 测试用例 9.2：跳过应用环境评价（一般问题）

**输入：**
```
形成性评价只在学习环境进行
没有考虑应用环境
```

**预期行为：**
- 插件应建议：考虑应用环境评价
- 应询问：学习者能否在工作中应用？
- 应设计迁移评价

**测试等级：** L3（一般问题）
